# Vector four-microphone board test

**Firmware finding.** Anki's sound-check behavior deliberately arms the raw recorder, plays an onboard animation tone, and checks its frequency independently on the back-left, front-left, back-right and front-right microphones, in that index order. This establishes design intent for simultaneous capture. The behavior controls head, lift, volume and stimulus itself. Its FFT result alone cannot supply the echo waveform. The inspected community-hosted source snapshot has not been matched to Unit 1's installed binary. [Sound-check implementation](https://github.com/kercre123/victor/blob/669ec7499a7084640b57706a7937884a6568be50/engine/aiComponent/behaviorComponent/behaviors/devBehaviors/selfTest/behaviorSelfTestSoundCheck.cpp#L49-L117)

**Signal path.** The active robot HAL passes body audio to the supervisor. Two interleaved 80-frame blocks become one message containing 160 samples grouped by microphone. The animation process queues that payload when the microphones are unmuted. Its raw loop copies samples into recording jobs before calling the single-channel speech pipeline, where speaker activity influences processing. The SDK playback component independently feeds the streaming audio engine. The raw job restores frame-interleaved channel order and writes a four-channel file ending in `_raw.wav` on a background thread. A completion message can precede file close. **Stock access is the open question.** The recorder accepts the internal engine message `StartRecordingMicsRaw`. The ordinary voice-message behavior requests processed audio. The alternative console command `RecordMicDataClip` requires remote-console support and its recording job requires `ANKI_DEV_CHEATS`. On a build exposing that command, the default clip is four seconds. The development pull script retrieves the micdata cache through the configured robot file-transfer facility. I found no public Python SDK operation to start and retrieve this four-channel recording. Verify an already available capture **and retrieval** route on the installed build before placing the board. Without one, record “raw access unavailable” and leave the physics result open. ## Bench procedure

1. Use the same quiet table and stationary robot for all five takes. Mark its footprint and head pose, the projected speaker position, and the board plane at 40, 60 and 80 cm along the forward axis. Center a rigid broad board at speaker height, perpendicular to that axis. Record board size, firmware version, pose, room temperature and playback settings. Keep hands clear during acquisition.
2. On the paired SDK host run `python hardware/play_board_probe.py --serial SERIAL` from the simulator directory. It connects once and pauses before each take. Arm raw capture first, then immediately press Enter. Each two-second playback contains eight identical 4 ms audible sweeps, 2–6 kHz, 200 ms apart. Leave the same speaker level for all takes. If using the debug recorder, collect the newest completed `*_raw.wav` under `/data/data/com.anki.victor/cache/micdata/debugCapture/`. Allow the writer to finish before copying. Keep originals.
3. Collect `open-before.wav`, `40.wav`, `60.wav`, `80.wav`, `open-after.wav` in one new directory. Remove the board completely for each open take. Check the first open take immediately with `PYTHONPATH=hardware python -c "from board_echo import capture; print(capture('takes/open-before.wav')[2])"` (adjust directory). All four channels must contain the eight direct arrivals above background, at regular intervals and without clipping. If clipped, lower playback volume and restart all five. If playback is audible and raw files have silence, truncation or fewer channels, retain the files and record that observation before attempting range.
4. With NumPy and SciPy installed, run `python hardware/board_echo.py analyze takes`. Inspect the printed channel delays and `takes/profiles.csv`, which contains all five direct-aligned, normalized correlation envelopes by channel. For replication, repeat in a fresh directory with 80, 40 and 60 cm acquired in a different order using the same probe and label files by actual distance.

## Interpretation

At 343 m/s the nominal round trips are 2.33, 3.50 and 4.66 ms. Speaker/mic offset and the direct path change the intercept. Each 20 cm move should shift a board echo by about 1.17 ms. The firmware WAV header is 16,000 Hz although SDK protocol documentation describes 15,625 Hz raw sampling. The analysis reports samples per playback second from the pulse cadence, so a stable clock ratio is visible and used for delays. This assumes playback follows its nominal timebase. It cannot determine absolute oscillator accuracy. [Firmware constants](https://github.com/kercre123/victor/blob/669ec7499a7084640b57706a7937884a6568be50/lib/micData/micDataTypes.h#L26-L32) · [SDK protocol](https://github.com/anki/vector-python-sdk/blob/master/anki_vector/messaging/messages.proto)

The analyzer takes the median of eight direct-aligned envelopes per channel. It searches the same 1.4–6.5 ms interval at all three distances, subtracts the mean of both open controls, and reports the strongest excess peak. The provisional screen requires a peak larger than both 1.5% of direct amplitude and three times the largest open-control drift in the interval. Both adjacent moves must shift by 1.17 ± 0.35 ms on the same three or more channels. Inspect the envelope shapes and repeat any positive result. Dominant multipath or a stronger reflection than the direct sound can misalign the profiles. A negative result bounds this particular probe and setup.

Offline end-to-end checks used the shipped probe, independent channel noise and four-channel PCM files. Moving reflections passed on 4/4 channels at both simulated clock rates, including a 15,625 Hz capture labeled 16 kHz. A fixed 3 ms reflection passed on 0/4. The loader rejected mono. These are synthetic checks. Physical capture and board discrimination are pending.
